# MNIST-12 — Catalyst N1 Matched Architecture Experiment

**Status:** In progress — pinned-source feasibility audit, semantic audit, graph-preserving CPU adapter, delivered-drive CPU adapter, matched-bundle runner, environment bootstrap, and regression coverage implemented; local Catalyst execution pending. Physical graph-preserving MNIST is already blocked at the pinned M13.5 K26 source boundary.

## Goal

MNIST-12 uses **Catalyst N1**, the same independent Loihi-class architecture audited in core M13, as an application-level comparison target for the unchanged frozen native-sparse MNIST workload.

Catalyst is not Intel Loihi. Its value here is that it provides an independently designed fixed-point/event-driven neuromorphic architecture with a Python reference simulator and open RTL, allowing us to ask:

> How does the same frozen MNIST graph behave under Catalyst's independently chosen LIF semantics, and which differences are graph/transport effects versus neuron-model effects?

## Frozen comparison contract

The primary workload is the same `mnist-v1/native-sparse` deployment used by MNIST-11:

```text
784 external axons
10 output neurons
4,086 nonzero effective connections
16 deterministic ticks
zero recurrent routes
same effective signed integer weights
same zero initial state
same spike-count decoder
no retraining
```

Both MNIST-11 and MNIST-12 consume the same backend-neutral bundle generated by:

```text
scripts/prepare_matched_reference_bundle.py
```

so images and input-event schedules cannot silently diverge across targets.

## Two Catalyst CPU experiments

Catalyst's generic pinned SDK and its reduced K26 wrapper have different capacity boundaries. MNIST-12 therefore preserves two explicit software experiments rather than conflating them.

### A. Graph-preserving CPU reference

The pinned generic SDK exposes `1024` neurons/core and a software-expanded connection pool. The frozen application can therefore be materialized on one software core as:

```text
784 source neurons + 10 output neurons = 794 neurons
4,086 exact effective-weight edges
```

`mnist_app/catalyst_matched.py` creates one source neuron per MNIST axon. An encoded event injects current `1` into that source; threshold `1` makes it emit a source spike. The exact `784 x 10` sparse effective-weight matrix is then compiled through Catalyst's own graph/compiler path.

Catalyst's synchronous pipeline delivers a newly generated source spike to its targets on the following native timestep. The runner therefore executes one pipeline-flush tick and compares:

```text
project canonical tick k  <->  Catalyst native output tick k+1
```

This is labeled:

```text
MATCHED EFFECTIVE GRAPH + TRANSLATED DYNAMICS
```

The Catalyst source encoding is not Loihi-style field-for-field weight encoding; only the accepted delivered effective weight is graph matched.

### B. Delivered-drive CPU reference

M13.3 already froze a second comparison path for exactly the neuron configuration used by MNIST:

```text
project current_decay = 4096
project voltage_decay = 0
zero bias/reset
```

Because current fully decays every tick, each external axon row can be collapsed into the exact ten per-target currents delivered that tick. The existing M13 `cpu_direct_drive` normalization maps:

```text
strict project V > T  -> Catalyst V >= T+1
zero voltage decay    -> Catalyst leak=0
project R=1 reference -> Catalyst refrac=0
```

MNIST-12 runs this view independently of the graph-preserving view. It is labeled:

```text
MATCHED DELIVERED DRIVE + TRANSLATED DYNAMICS
```

The two Catalyst views are an internal control. If their spike-count vectors/predictions disagree after the declared one-tick graph alignment, the CLI fails because the adapter itself needs review. By contrast, a Catalyst-vs-project mismatch is preserved as a valid architecture result.

## Refractory mapping

The same explicit project `R=0 -> R=1` equivalence proof used by MNIST-11 is required before Catalyst execution. Catalyst then receives the already-frozen M13 transform `canonical R=1 -> native refrac=0`.

No direct `0 -> 0` assumption is made without the project-side equivalence gate.

## K26 feasibility result known before application execution

M13.5 froze the strongest source-supported Catalyst K26 boundary. The pinned `fpga/kria` wrapper is **not the same capacity as the generic SDK**:

```text
configured cores:          2
neurons/core:              256
total configured neurons: 512
pool depth/core:           4096
clock target:              100 MHz
upstream target part:      xczu5ev-sfvc784-2-i
```

The graph-preserving MNIST construction requires `794` neuron slots, so it **does not fit** this pinned wrapper configuration.

Furthermore M13.5 established that the pinned K26 source has:

- no board XDC;
- no PS/block-design integration;
- no `write_bitstream` step; and
- AXI interfaces exposed as top-level ports.

M13 successfully reproduced routed implementation, but physical KV260 programming/execution was not source-supported.

Therefore MNIST-12 currently records:

```text
generic Catalyst CPU graph-preserving experiment: SUPPORTED
Catalyst CPU delivered-drive experiment:          SUPPORTED
pinned K26 graph-preserving MNIST:                 BLOCKED (794 > 512 neurons)
pinned K26 physical delivered-drive MNIST:         BLOCKED by board integration and not graph matched
```

This is not a failed experiment. It is a concrete capacity/platform result. A future custom Catalyst board integration or reparameterized hardware configuration would be a **new implementation experiment** and must be labeled as such rather than attributed to the pinned upstream K26 artifact.

## Interpretation rules

- Catalyst disagreement with FPGA-v1 is not automatically a failure.
- The first divergent tick/state is more informative than only final accuracy.
- CPU wall time is not compared to FPGA PL latency.
- M13.5 resource totals are not used to claim Catalyst/FPGA efficiency ranking.
- No power/energy comparison is admitted from Vivado estimates or board TDP.
- No target-specific retraining is allowed in the primary matched experiment.
