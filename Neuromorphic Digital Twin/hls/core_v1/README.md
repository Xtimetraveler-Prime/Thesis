# M11 HLS Computational Core

This directory implements the hardware-facing path from the frozen M10 FPGA-v1 computational-core specification into Vitis HLS RTL and a Vivado IP Integrator project.

## Standard M11 toolchain

M11 and later FPGA-development work standardize on:

```text
AMD Vitis  2025.2
AMD Vivado 2025.2
```

The command-line flow uses the 2025.2 tools:

- `vitis-run --mode hls --csim` for C simulation;
- `v++ -c --mode hls` for HLS synthesis;
- `vitis-run --mode hls --cosim` for C/RTL co-simulation;
- `vitis-run --mode hls --package` for Vivado-IP packaging;
- `vivado -mode batch -source ...` for scripted project/IP-Integrator construction.

The repository does not rely on legacy `vitis_hls -f ...` scripts or a GUI-only Vivado project state as the primary M11 reproduction path.

## Current verified HLS top

M11.1 established the smallest useful synthesis boundary: one complete neuron state transition. The HLS top function is:

```text
neuron_step_v1(...)
```

It consumes current, voltage, refractory state, already-accumulated integer synaptic input, current/voltage decay, threshold, bias, reset voltage, and configured refractory duration. It produces next current, next voltage, next refractory state, and spike/no-spike.

The current HLS boundary intentionally does not contain synapse-memory traversal, recurrent routing, or the multi-neuron tick scheduler. M11.5 integrates those around this already verified datapath instead of weakening the single-neuron verification boundary.

## Frozen M10 semantics implemented

The C++ datapath follows the FPGA-v1 contract rather than relying on native C/C++ overflow behavior:

```text
I_work = SAT24(I0 + S)
I_next = SAT24(DECAYED(I_work, current_decay))
```

For a non-refractory neuron:

```text
V_decay_base = DECAYED(V0, voltage_decay)
V_work       = SAT24(V_decay_base + I_work + bias)
spike        = (V_work > threshold)
```

A spike hard-resets voltage and loads `max(refractory_ticks - 1, 0)`. A blocked refractory tick still updates current, holds voltage at reset voltage, suppresses spiking, and decrements the refractory counter.

Decay removes:

```text
round_away_from_zero(value * decay / 4096)
```

Because `4096 == 2^12`, the HLS implementation computes the magnitude ceiling with an add-and-shift operation while preserving the exact M10 integer result.

## HLS widths

The frozen architectural state uses:

- `ap_int<24>` current and voltage;
- `ap_uint<16>` refractory state;
- `ap_uint<13>` decay configuration;
- `ap_uint<1>` spike output.

The current HLS boundary uses a signed 64-bit integer for the already-accumulated synaptic-input scalar and intermediate arithmetic. M11.2 deliberately limited randomized synaptic-input vectors to signed 32-bit values: that range is large enough to stress both SAT24 boundaries without falsely freezing the final physical accumulator/event capacity. M11.5 is responsible for freezing that finite hardware capacity.

## M11.1 C-simulation gate — complete

The original self-checking C++ testbench contains 11 hand-written directed cases. The independently reproduced M11.1 vendor run under Vitis 2025.2 finished with:

```text
M11.1 HLS neuron-step tests passed: 11 cases
```

This established that the HLS C++ source compiles under the selected vendor toolchain and reproduces the directed M10 equations.

## M11.2 Python-to-HLS differential gate — complete

M11.2 extends C simulation so expected values come directly from the frozen Python FPGA-v1 profile instead of being hand-copied into C++.

The Python source of truth is:

```text
NeuronState + NeuronConfig
          ↓
step_neuron(..., arithmetic=FPGA_CORE_ARITHMETIC_V1)
          ↓
expected current / voltage / refractory / spike
```

`src/neuromorphic_twin/hls_conformance.py` generates the comparison corpus and `examples/generate_m11_hls_vectors.py` provides its CLI. The standard corpus is deterministic:

```text
directed boundary cases: 24
seeded random cases:   2048
---------------------------
total:                 2072
seed:             0x4D313132
```

The pseudo-random stream is generated by an explicitly implemented SplitMix64 sequence rather than Python's library RNG, so the corpus is tied to the stored algorithm and seed rather than a Python-version-specific random implementation.

The independently reproduced Vitis 2025.2 C-simulation gate finished with:

```text
M11.1 HLS neuron-step tests passed: 11 cases
M11.2 Python/HLS differential tests passed: 2072 cases (directed=24, random=2048, seed=0x4d313132)
```

Every vector compares current, voltage, refractory state, and spike exactly.

## Running the combined M11.1 + M11.2 C simulation

First source the Vitis/Vivado 2025.2 environment and export the frozen target part:

```bash
export HLS_PART='xck26-sfvc784-2LV-c'
```

Then, from this directory:

```bash
bash run_csim.sh
```

Because the repository path contains `Neuromorphic Digital Twin`, the wrapper stages the HLS component under `/tmp/neuromorphic_twin_hls_<uid>/...` before invoking Vitis; Vitis HLS 2025.2 rejects project/solution paths containing spaces.

## M11.3 HLS synthesis + C/RTL co-simulation — complete

M11.3 converted the behaviorally verified C++ into generated RTL for the selected K26 target and verified that RTL against the same Python-golden corpus.

### Frozen synthesis baseline

```text
target part:         xck26-sfvc784-2LV-c
HLS clock period:    10.000 ns (100 MHz)
clock uncertainty:    1.200 ns (12%)
flow target:          Vivado
RTL output format:    rtl
```

The independently reproduced synthesis report records:

```text
Estimated clock:      8.785 ns
Estimated Fmax:     ~113.83 MHz
Latency:              1 cycle
Transaction interval: 2 cycles
Pipeline:              no

BRAM_18K:              0
DSP:                   2
FF:                   51
LUT:                1418
URAM:                  0
```

The two DSP instances are the two 24-bit-by-13-bit decay multipliers. The remaining datapath is primarily LUT-based add/subtract, comparison, saturation/select, and control logic.

The final HLS interface is:

- global `neuron_step_v1(...)` top for Vitis 2025.2 co-simulation compatibility;
- `ap_ctrl_hs` transaction control;
- `ap_none` scalar inputs;
- `ap_vld` output pointers/results.

The final RTL co-simulation completed XSIM and C post-checking with:

```text
M11.1 HLS neuron-step tests passed: 11 cases
M11.2 Python/HLS differential tests passed: 2072 cases (directed=24, random=2048, seed=0x4d313132)
INFO: [COSIM 212-1000] *** C/RTL co-simulation finished: PASS ***
```

That establishes exact Python → HLS C++ → generated RTL agreement at the isolated neuron transition boundary.

Run the reproducible M11.3 flow with:

```bash
export HLS_PART='xck26-sfvc784-2LV-c'
bash run_m11_3.sh | tee m11_3_2025_2.log
```

## M11.4 Vivado IP packaging + project integration — complete

M11.4 packages the M11.3-verified RTL as custom Vivado IP and places it in a reproducibly generated K26-targeted Vivado/IP-Integrator project.

The packaged identity is:

```text
neuromorphic-twin.org:hls:neuron_step_v1:1.0
```

`hls_package.cfg` selects `package.output.format=ip_catalog`, and `run_m11_4.sh` performs fresh HLS synthesis, packaging, preservation of the generated IP repository/ZIP, and batch-mode Vivado project creation.

`vivado/create_m11_4_project.tcl`:

- creates `neuromorphic_twin_m11_4` for `xck26-sfvc784-2LV-c`;
- registers the custom IP repository using `IP_REPO_PATHS` and `update_ip_catalog`;
- verifies the expected VLNV;
- creates block design `neuromorphic_twin_core`;
- instantiates `neuron_step_v1_0`;
- externalizes the complete `ap_ctrl_hs` interface rather than manually overriding only `ap_start`;
- externalizes the remaining scalar HLS ports;
- validates and saves the BD;
- generates block-design HDL/output products and the HDL wrapper.

Tooling fixes made while closing M11.4 include removing an invalid zero-argument `save_project`, preserving `ap_ctrl_hs` as a complete IP-Integrator interface, moving `get_bd_ports` reporting while the BD is still current/open, and removing redundant generated project/BD Tcl snapshots that embedded local build paths.

The independent completion verification confirmed both the generated Vivado project and block design exist:

```bash
test -f build/m11_4/vivado_project/neuromorphic_twin_m11_4.xpr \
  && echo "XPR: PASS"

find build/m11_4/vivado_project \
  -type f -name 'neuromorphic_twin_core.bd' -print
```

Both checks passed after the final scripted Vivado run. Detailed M11.4 design/reproduction notes are in `vivado/README.md`.

Run the complete M11.4 flow with:

```bash
export HLS_PART='xck26-sfvc784-2LV-c'
bash run_m11_4.sh | tee m11_4_2025_2.log
```

## Next: M11.5 integrated computational core

M11.5 turns the isolated packaged neuron transition into the first complete FPGA computational core. The next integration layer must add:

- neuron state/configuration storage;
- M08-compatible weight-format, synapse, and CSR axon-row storage;
- deterministic synaptic traversal and accumulation with a finite physical capacity profile;
- a multi-neuron/tick controller preserving the six M10 behavioral phases;
- next-tick recurrent event routing from M09/M10;
- trace/debug observability suitable for M12 comparison.

M11.5 will keep the source-controlled scripted Vivado flow as the normative project generator. Vivado GUI use may still be useful for inspecting the resulting block diagram and reports, but the architecture should not depend on manual GUI edits that cannot be recreated from the repository.
