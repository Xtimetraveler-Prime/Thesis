# P03.2c — Physical Cortex-A53 MMIO Smoke

**Status:** Verification candidate  
**Phase:** P03 — Autonomous PS-resident runtime  
**Sub-milestone:** P03.2c — Physical PS-MMIO smoke  
**Branch:** `agent/v3-p03-autonomous-runtime`  
**Date drafted:** 2026-10-06

## Purpose

P03.2a proved the AXI4-Lite control-register contract in simulation.

P03.2b proved that the PS-visible HPM0/MMIO shell routes on K26 and exports a
fixed XSA.

P03.2c proves the next physical boundary:

> Can Cortex-A53 software, rather than JTAG/VIO command ownership, physically
> read the P03 MMIO endpoint and issue page, resident-memory, and dispatch
> commands through it?

This is a smoke test of the physical PS-to-PL command plane. It is not yet the
full P03 scheduler/router/barrier runtime.

## Standalone software flow

The P03.2c application is built from the accepted fixed XSA with the Vitis 2025.2
Python API.

The platform is:

```text
OS:           standalone
processor:    psu_cortexa53_0
architecture: 64-bit
compiler:     gcc
domain:       standalone_psu_cortexa53_0
```

Primary build files:

```text
software/p03/build_p03_2c_smoke.py
software/p03/p03_2c_smoke.c
software/p03/include/p03_mmio.h
scripts/build_p03_2c_smoke.sh
```

The build gate rejects any loadable ELF segment that overlaps the project
backing window:

```text
0x40000000 .. 0x43FFFFFF
```

This smoke-level check does not replace the explicit P03.3 standalone linker
reservation required by the P03.1 runtime contract.

## Physical fixture

The smoke fixture reconstructs the exact accepted P02.4b five-core directed ring
and extracts logical core 0's initial 512 KiB backing record.

The P03.2c preflight requires that this record be byte-identical to the core-0
record generated by the accepted `p02_4b_ring_fixture.py`.

Physical locations:

```text
core0 backing record: 0x40000000
result mailbox:       0x43FF0000
```

The mailbox lies in the reserved tail of unused logical record 127. It is
outside the ten-bank resident payload transferred by the P02 page walker.

## Board preparation boundary

As in accepted P02 physical bring-up:

1. boot the KV260 far enough for the normal PS path to initialize DDR;
2. halt all visible Cortex-A53 cores;
3. select the non-processor PSU target, with APU fallback, for physical DDR
   provisioning;
4. provision the accepted core-0 record and clear the mailbox;
5. verify both by physical readback;
6. program the accepted P03.2b bitstream;
7. use VIO only for one **pre-run reset pulse**;
8. download the standalone ELF to Cortex-A53 #0;
9. let the A53 application execute;
10. read the final mailbox through the physical PSU/APU target;
11. stop the A53 and reboot the board rather than resuming the halted Linux
    instance.

## Command ownership

During the active smoke application, the PC does **not** issue:

- page commands;
- dispatch commands;
- resident-memory commands.

The Cortex-A53 application performs those operations by writing the P03
AXI4-Lite MMIO registers.

VIO output ownership is restricted to the pre-run reset request.

## Physical operations

The A53 application performs these steps in order.

### 1. MMIO identity

Read and require:

```text
ID           = 0x4C543302
VERSION      = 0x00010000
CAPABILITIES = 0x0001031F
```

The capability value encodes the three command classes, 64-bit DDR addressing,
256-bit resident data, three resident slots, and one physical engine.

### 2. Real DDR page-in

Command:

```text
PAGE_IN
resident_slot = 0
record_base   = 0x40000000
mutable_only  = 0
```

Require:

```text
done = 1
errors = 0
semantic bytes = 438272
AXI read bursts = 1712
AXI write bursts = 0
pending write bytes = 0
```

This is the accepted full 428 KiB resident payload transfer.

### 3. Resident-memory read through MMIO

Read:

```text
resident slot = 0
bank          = config
word address  = 0
```

and require the returned low word to match the accepted core-0
`config[0]`.

This exercises:

```text
A53
 -> HPM0
 -> p03_ps_control_regs
 -> accepted P02 page/debug arbiter
 -> resident URAM
 -> latched MMIO response
 -> A53
```

### 4. One HLS dispatch through MMIO

Dispatch logical core 0 from resident slot 0 with:

```text
timestep         = 0
event_read_bank  = 0
event_count      = 0
```

The accepted core metadata still describes its real compartment/synapse/route
image, but zero current events intentionally make this a command-plane smoke
rather than an algorithmic workload.

Require:

```text
done = 1
errors = 0
packet_count = 0
core_status = 0
completed_dispatches = 1
active logical core = 0
active slot = 0
active event bank = 0
```

## Machine-readable result mailbox

The standalone app writes a 64-byte result structure at `0x43FF0000`.

It includes:

- magic/version;
- PASS/fault code;
- MMIO ID/version/capabilities;
- final global status;
- page status/bytes/read/write bursts;
- resident-read status and config word;
- dispatch status and completed-dispatch count.

The app flushes this mailbox from the A53 cache before entering a permanent
`WFE` loop.

The host verifies the mailbox with:

```text
scripts/p03_2c_verify_mailbox.py
```

Thus physical success is based on state written by the A53 application, not on
JTAG/VIO inference.

## P03.2c acceptance boundary

P03.2c is accepted when an independent physical run produces:

```text
PASS: P03.2c mailbox verified ...
PASS: P03.2c physical Cortex-A53 MMIO smoke gate completed successfully.
```

with the accepted P03.2b artifact hashes.

A P03.2c pass closes overall P03.2.

It does **not** prove autonomous scheduling, routing, barrier ownership, or
multi-timestep execution. Those begin in P03.3.
