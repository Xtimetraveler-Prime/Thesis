# P04 Multicore Routing and Barrier Architecture

## Status

P04 architecture decision and implementation contract. This document is subordinate to `docs/LOIHI1_TARGET_SPEC.md` and preserves the accepted P03 one-core behavior.

P04 adds packet transport and global algorithmic-timestep completion semantics. It does not change neuron arithmetic, per-core Loihi resource limits, packet destination semantics, or the distinction between algorithmic timesteps and FPGA clock cycles.

## 1. Architectural purpose

P03 ends at a normalized egress packet record for one logical core. P04 connects multiple logical-core endpoints through an explicit packet fabric and proves that a timestep cannot advance until:

1. every participating logical core has completed its current compartment update;
2. every packet generated by that update has been accepted by the routing fabric; and
3. every such packet has been delivered into its destination ingress boundary for the subsequent architectural update.

A spike generated while evaluating algorithmic timestep `t` continues to target `t + 1`. Routing and draining therefore happen between those two architectural updates; FPGA service cycles used to move the packet are not additional Loihi timesteps.

## 2. Existing golden-model semantics reused by P04

The Python model already contains the semantic oracle P04 hardware must match:

- `LogicalChip` owns multiple independently configured `LogicalCore` instances.
- `SpikePacket` carries destination core, destination axon, target timestep, and optional source metadata.
- each firing compartment expands its output route list into explicit per-destination packets;
- `PacketRouter` queues packets independently of core execution order;
- `BarrierCoordinator` tracks core completion and in-flight packet count;
- `LogicalChip.advance()` is illegal until all participating cores are complete and the router is empty;
- incoming packets affect the destination's subsequent architectural update;
- normalized traces sort architecturally unordered packet/contribution sets so legal service-order changes do not alter the normalized result.

P04.1 additionally classifies generated traffic as `local` when source and destination logical core IDs match and `remote` otherwise. Both classes pass through the same logical barrier contract. This is a project-level modeling choice; it does not claim that native Loihi physically transports both cases identically.

## 3. P03 hardware that remains reusable

The following P03 pieces are retained without changing their architecture-level meaning:

- `loihi_core_v2_tick` HLS engine and its one-timestep execution semantics;
- P03 configuration/state/axon/synapse/route memory word formats;
- 32-bit output-route records containing destination core and destination axon;
- 64-bit egress packet records containing destination core, destination axon, source compartment, and target timestep;
- Python P03 image packing/unpacking and normalized comparison code;
- the HLS `ap_ctrl_hs` start/done integration rule established during P03;
- XPM-based memory shells where a P04 endpoint needs physically retained local memory;
- VIO/JTAG observability patterns and physical cycle instrumentation.

P04 does not reinterpret the P03 packet word. Source-core identity is supplied by the endpoint/router port because it was implicit in the one-core P03 engine.

## 4. The K26 BRAM constraint

The accepted full-capacity P03 shell uses 96.5 of the K26's 144 BRAM tiles. Blindly duplicating that shell would require approximately 193 BRAM tiles before adding router queues or barrier logic, so two simultaneous full-capacity P03 memory images cannot fit in BRAM.

This is a physical implementation constraint, not a reason to change the logical Loihi model. P04 therefore keeps the source-backed logical limits unchanged:

- 1,024 compartments per logical core;
- 4,096 input axon IDs per logical core;
- 4,096 output route slots per logical core; and
- 128 KiB modeled synaptic fan-in storage per logical core.

### Options considered

1. **Duplicate two complete P03 shells.** Architecturally simple, physically infeasible on K26 BRAM.
2. **Shrink the logical core capacities.** Physically easy but rejected because it changes the modeled architecture merely to fit the FPGA.
3. **Move large per-core storage to URAM/DDR immediately.** Potentially feasible but changes the physical memory architecture substantially and risks turning P04 into a memory-system project before routing semantics are proven.
4. **Virtualize multiple full logical contexts through one physical core now.** Feasible in principle, but this is the explicit goal of P05 and would collapse the roadmap boundary.
5. **Use a resource-scaled P04 validation shell while retaining full logical capacities in the architecture.** The two endpoint compute engines remain the same P03 HLS logic, but the directed P04 physical test shell only instantiates enough backing memory for the test deployment. This proves genuine two-endpoint routing/barrier behavior without claiming that the P04 shell can simultaneously retain two maximally filled logical cores. P05 then solves full logical-context storage and scheduling transparently.

P04 adopts option 5, preceded by a standalone router/barrier RTL gate. Any resource-scaled memory used for a directed P04 hardware corpus is explicitly a **physical validation allocation**, not a new logical capacity.

## 5. P04 hardware architecture

```text
             core 0 P03-compatible endpoint
                      |
                      | packet valid/ready
                      v
              +-------------------+
              |                   |
              | P04 packet router |----> destination 0 ingress queue
              | + queueing        |
              | + traffic counts  |----> destination 1 ingress queue
              |                   |
              +---------+---------+
                        |
                        | pending / delivered accounting
                        v
              +-------------------+
core-done --->| P04 barrier       |---> advance permit
              | coordinator       |
core-done --->|                   |
              +-------------------+
                      ^
                      |
             core 1 P03-compatible endpoint
```

### 5.1 Ingress arbitration

Each producer has an independent one-entry capture slot so two cores may present packets simultaneously without loss. A deterministic arbiter services captured producers into destination queues. Arbitration order is an implementation detail and may be reversed during verification; normalized architectural results must remain unchanged.

Backpressure is explicit. A source packet is accepted only when its capture slot is available. A captured packet remains pending until its destination queue can accept it.

### 5.2 Destination queues

The initial two-core P04 fabric uses one FIFO per destination endpoint. Delivery completes only when the destination side consumes the queued packet. Pending producer slots plus destination FIFO occupancy form the fabric's in-flight count.

The first standalone RTL gate uses small register-array FIFOs for fast simulation. Queue depth is parameterized so the implementation can later move to XPM/BRAM without changing the handshake or architectural contract.

### 5.3 Local versus remote traffic

A packet is `local` when the producer logical-core ID equals the destination logical-core ID, otherwise it is `remote`. Both are conserved, queued, and included in quiescence detection. Separate counters expose the distinction for normalized/debug traces.

This explicitly models different logical route classes while avoiding an unsupported claim about native Loihi's exact physical local bypass implementation.

### 5.4 Barrier

For an active timestep, the coordinator latches completion from both endpoints. `can_advance` is true only when:

```text
all endpoints complete
AND no producer capture slot contains a packet
AND all destination queues are empty
```

An attempted advance before this condition is rejected/flagged. The next timestep may start only after a successful advance acknowledgement.

### 5.5 Packet integrity checks

The P04 fabric validates the P03 packet boundary that it consumes:

- packet `valid` bit must be asserted;
- destination core must name a configured endpoint;
- target algorithmic timestep must equal active timestep + 1.

Violations are implementation status errors and never silently index a queue or endpoint.

## 6. P04 versus P05

P04 answers: **given multiple logical-core endpoints, are packets routed and algorithmic time synchronized correctly?**

P05 answers: **how can multiple full logical-core contexts be retained and scheduled when the FPGA cannot physically instantiate one full memory shell per logical core?**

The interface between the phases is deliberate. P05 may replace the P04 physical endpoint allocation with a virtualized scheduler/context store while leaving the packet router, packet format, barrier invariant, and normalized traces unchanged.

## 7. Sub-milestones

### P04.1 — Golden-model contract closure

- make local/remote traffic explicit in normalized traffic accounting;
- add simultaneous-producer and fan-in regressions;
- retain feed-forward, multicast, recurrent, barrier-blocking, and service-order-invariance tests.

Gate: targeted multicore pytest plus full v2 pytest.

### P04.2 — Standalone packet-router/barrier RTL

- two producer capture slots with ready/valid backpressure;
- deterministic/reversible arbitration;
- two destination FIFOs;
- packet destination/timestep validation;
- local/remote traffic counters;
- core completion and quiescence detection;
- blocked-advance behavior.

Gate: XSim directed RTL test covering simultaneous producers, local/remote packets, backpressure/drain, reversed arbitration, and advance blocking.

### P04.3 — Two-endpoint P03-core integration shell

- instantiate two P03-compatible HLS compute endpoints;
- use explicitly resource-scaled physical backing memories sized for the directed P04 corpus while preserving the full logical capacity contract in Python/specification;
- convert delivered packet destination axons into the destination endpoint's next-timestep input-event list;
- run feed-forward, bidirectional/recurrent, simultaneous-producer, and multicast cases against Python normalized traces.

Gate: HLS/RTL simulation and integration synthesis.

### P04.4 — K26 implementation/resource gate

- route the P04 shell at 100 MHz;
- report LUT/register/BRAM/URAM/DSP use separately from logical Loihi occupancy;
- record timing and queue/resource implementation observations;
- generate bitstream only after timing/resource acceptance.

Gate: routed Vivado implementation.

### P04.5 — Physical multicore conformance

- load the directed P04 corpus through the hardware harness;
- execute multiple timesteps on K26;
- compare normalized core state, packet traffic, barrier state, and status with Python;
- rerun with an alternate legal packet-service/arbitration order where the hardware control permits it.

Gate: physical K26 output reports PASS. Only physical-board evidence closes this gate.

## 8. Non-goals for P04

P04 does not yet claim:

- simultaneous full-capacity physical retention of two maximally populated logical cores on K26;
- transparent logical-core virtualization;
- native Loihi asynchronous router timing or exact 8x4 physical mesh replication;
- exact native Loihi packet bitfields;
- programmable nonzero synaptic delays;
- online learning.
